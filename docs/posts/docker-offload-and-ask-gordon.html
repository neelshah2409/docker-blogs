Docker Offload and Ask Gordon: What Cloud-Burst AI Development Actually Looks Like

Two recent Docker Desktop features solve two different halves of the same problem: your laptop can't run the model, and even when it can, something's usually broken. Offload handles the first. Gordon's new sidebar handles the second, without you leaving what you were looking at.

Estimated time 8 min Format feature spotlight Covers 2 features
docker offload

Burst the GPU-heavy work, keep the local workflow

A GPU-accelerated model build or inference run doesn't care that your laptop only has integrated graphics. Docker Offload's answer is to swap where the command actually executes, not how you write it: docker offload start switches your Docker context to a managed cloud environment, and every subsequent docker build or docker run executes there instead of locally — same CLI, same Dockerfiles, same compose files.

Cloud context

A Docker context pointed at Docker's managed infrastructure instead of your local engine — switching back is one command, docker offload stop.

GPU provisioning

Offload can attach a cloud GPU instance to the session, giving a laptop with no discrete GPU access to real accelerated hardware on demand.

GPU-minute billing

Usage is metered by GPU-minute rather than by a flat subscription, after an initial block of free credits.

Turn it on, confirm it, turn it off
# Switch to a cloud context — you'll be asked whether you need GPU support
docker offload start

# Confirm the session is actually running in the cloud
docker offload status

# Everything after this runs on Docker's infrastructure, same commands as always
docker build -t my-model-image .

# Back to your local engine when you're done
docker offload stop

A Compose file that reserves a GPU doesn't need to change at all for this to work:

compose.yaml — unchanged, just running somewhere else
services:
  trainer:
    image: my-training-image
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
ask gordon

From a dedicated tab to a sidebar that already knows what's wrong

Gordon — Docker Desktop's built-in AI assistant — used to live on its own page. Asking it about a failing container meant leaving that container's screen entirely, describing the problem from memory, and losing your place. The recent update moves Gordon into a persistent sidebar that slides in over whatever you're already looking at, so the context never gets dropped in the first place.

The more useful change sits one level down: containers, images, and volumes with a detected issue now show a Gordon indicator directly on their row. Click it, and Gordon starts a diagnosis immediately — it already knows which resource you clicked and what's wrong with it, rather than waiting for you to explain.

practical scenario

What a session actually looks like using both together

The two features solve different problems, but a normal session uses them back to back rather than as separate tools you consciously switch between.

1
Develop locally, as usual
Write and iterate on the application code on your own machine — no reason to pay for cloud GPU time for work that doesn't need one.
2
Offload only the heavy step
docker offload start, run the GPU-bound build or training step, then docker offload stop the moment it's done — you're not paying for idle cloud time between runs.
3
Something breaks — check the row, not a search bar
A container that failed to start shows the Gordon indicator right on its row in Docker Desktop.
4
Click it, get a diagnosis, stay put
Gordon opens in the sidebar already scoped to that exact container — no re-explaining what you were looking at, no lost context.

Nothing here required a different mental model for either feature — Offload changes where a command runs, and Gordon changes how far you have to travel to ask about something. Neither one asks you to restructure how you already work.

Worth checking before you commit a workflow to this

Offload's access model, free-credit allowance, and per-GPU-minute pricing have all been in active flux since launch, and at points required a separate beta signup on top of a recent-enough Docker Desktop version. None of that makes it unusable — it makes it worth reading the current Offload docs immediately before you build a workflow around it, rather than relying on last month's blog post (including this one) for the exact limits.
