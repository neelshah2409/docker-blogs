MicroVMs vs Containers vs Full VMs: The Architecture Behind Docker Sandboxes

"Sandboxed" isn't one thing — a full VM, a container, Docker-in-Docker, and a microVM all claim to isolate untrusted code, but they draw the boundary in completely different places, at completely different costs. Here's what's actually happening underneath each one.

Estimated time 22 min Difficulty advanced Assumes containers & VMs basics
context

Why the isolation model matters more once an agent is driving

A human developer running untrusted code in a container makes hundreds of small judgment calls without noticing: don't mount the home directory, don't run as root, glance at the diff before applying it. An autonomous agent makes none of those calls unless the sandbox makes them for it. That shifts the question from "is this container reasonably safe" to "what, precisely, is the kernel-level guarantee here" — because the agent will eventually generate the one command a human wouldn't have typed.

That precision is exactly where "container" as a catch-all term breaks down. A full VM, a plain container, Docker-in-Docker, and a microVM all get called "isolated," but they isolate at different layers of the stack, and those layers have very different failure modes.

Kernel isolation

Whether a workload runs against its own kernel or shares the host's. Sharing means one kernel exploit reaches every workload on the box.

Attack surface

Everything an untrusted workload can touch before hitting a boundary it can't cross — device drivers, syscalls, shared sockets, mounted paths.

Cold-start cost

The time and memory it takes to bring a fresh isolated environment online — the tax you pay for isolation, paid on every single run.

the four models

Full VM, container, Docker-in-Docker, and microVM — compared

Four approaches show up constantly in agent-sandboxing conversations, often used loosely as if they're interchangeable. They aren't.

The pattern worth noticing: a full VM and a microVM offer the same category of guarantee — a real, separate guest kernel — for wildly different costs. A container and Docker-in-Docker offer the same category of weakness — a shared host kernel — no matter how the nesting is arranged.

the anti-pattern

Why Docker-in-Docker breaks isolation guarantees for agents

"Docker-in-Docker" almost always means one of two things, and both quietly hand back the isolation a sandbox was supposed to provide.

Approach 1 — mount the host's socket

The container is given /var/run/docker.sock from the host. Every docker command the agent runs inside its "sandbox" isn't talking to a nested daemon at all — it's talking directly to the real Docker daemon on your actual machine. The container walls are still up, but the thing behind them has a direct line to the host.

Approach 2 — nested daemon with --privileged

A real Docker daemon runs inside the container, which requires --privileged to get the device access and kernel capabilities a daemon needs. That flag doesn't grant one capability — it strips away nearly every namespace and cgroup restriction Docker normally applies, which is most of what made it a "sandbox" in the first place.

      common misconception
      

        What people assume
        
"Docker-in-Docker inside a container is basically the same thing as a microVM, just with an extra layer."

        
What's actually true

        
They aren't in the same category. DinD, in either form, still runs against one shared host kernel — the "extra layer" is either a socket back to that same kernel or a privilege-stripped container on top of it. A microVM adds an actual second kernel, booted inside a hardware-virtualized boundary (via KVM), that the guest cannot see past no matter what runs inside it. No amount of nesting containers recreates that; it requires a hypervisor.

      

    


    
    

      performance tradeoffs
      
The cold-start cost of each isolation level

      
Stronger isolation has historically meant slower and heavier — a full VM's dedicated kernel comes from emulating an entire computer's worth of hardware: disk controllers, network cards, a BIOS, sometimes a graphics device. That emulation is also most of where full VMs spend their 30–60 second boot time and hundreds of megabytes of overhead.

      
MicroVMs, popularized by AWS's open-source Firecracker project for Lambda and Fargate, get most of the way to VM-level isolation by throwing out almost all of that emulated hardware. A Firecracker microVM exposes roughly half a dozen minimal virtio devices instead of a full emulated machine — which is most of why it can start a guest kernel in around 125 milliseconds with under 5MB of memory overhead, and why a single host can create on the order of a hundred or more of them per second.

      decision framework
      
Which model actually fits your workload

      

        

          
WorkloadRecommended modelWhy

          
CI step running your own reviewed codeContainerLow stakes, low overhead — the code is already trusted

          
Autonomous agent with shell + Docker accessmicroVM, isolated daemonUntrusted, unsupervised, needs a real kernel boundary at low latency

          
Multi-tenant platform running arbitrary customer codemicroVMMany strangers' workloads on one host — kernel sharing isn't acceptable

          
Long-lived dev environment needing full OS featuresFull VMBoot cost amortizes over hours or days of use — isolation strength matters more than cold start

        

      

      
The through-line: the moment untrusted, unsupervised code is involved, the shared-kernel models — container and Docker-in-Docker — are disqualified regardless of convenience. The choice that's actually left is boot-time cost (full VM) versus near-container speed (microVM), and for anything that spins up per task or per session, that usually settles it.
