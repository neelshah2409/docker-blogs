Inside Docker's MCP Gateway: Securing the Bridge Between Agents and Tools

The moment an agent can reach more than one tool server, something has to decide which servers exist, which specific tools an agent may call, and how a request actually gets from the agent to the right container. That something is the gateway — and what it does and doesn't enforce is worth understanding precisely.

Estimated time 21 min Difficulty advanced Assumes MCP basics
what it actually does

Discovery, access control, and message routing — not one thing

"MCP Gateway" gets described as a single feature, but it's really three separate jobs, and conflating them is where most misunderstandings about what it secures come from.

Discovery

Which MCP servers exist at all for this session — pulled from a catalog, not hardcoded per agent.

Access control

Of the servers that exist, which specific tools an agent may actually call — down to individual tool names, not just whole servers.

Message routing

Once a call is allowed, getting the request to the right containerized server and the response back — the gateway is the only thing either side talks to directly.

Each MCP server the gateway manages runs in its own container, so the gateway is also the only component that needs network access to spawn and supervise them — the agent itself never talks to a tool server directly, only to the gateway's single endpoint.

      context bloat
      
Smart Search and Tool Composition

      
Give an agent direct access to hundreds of tools across a dozen MCP servers, and the standard protocol behavior — listing every tool's full definition up front — starts working against you. A single tools/list call across a handful of well-populated servers can run into the tens of thousands of tokens before the agent has taken a single action, and once dozens of similarly-named tools are all sitting in context together, model accuracy on picking the right one measurably drops.

      
Docker's answer is to stop loading every tool definition by default. Smart Search exposes a small, constant set of discovery tools instead — the agent searches for what it needs by intent, and only the matching tool's definition enters context. Tool Composition goes a step further, letting an agent write code that combines existing tools into a new, reusable one inside a sandboxed execution step, instead of chaining many separate round-trips through the gateway.

      a documented, patched risk pattern
      
What happens when the gateway trusts its caller too much

      
Worth understanding as a cautionary example, not a how-to: in late 2025, security researchers publicly disclosed a vulnerability in Docker's "Ask Gordon" AI assistant, patched in Docker Desktop 4.50.0. The general mechanism — since patched, and described here at the level public reporting already covers, with no exploit detail — is what matters for this post's argument.

      

        The pattern, at a summary level
        
Docker image metadata (label fields) can contain arbitrary text, since labels are meant to be descriptive, not executable. Ask Gordon, when asked about an image, read that metadata as context — and forwarded what it found to the MCP Gateway as if it were a legitimate instruction from the user. The gateway, seeing what looked like a normal request from a trusted caller, invoked the corresponding tools without additional validation. Researchers termed this "Meta-Context Injection": the failure wasn't in the gateway's routing logic, it was in nothing upstream of the gateway distinguishing data an assistant reads from instructions a user actually gave.

      

      
The fix Docker shipped is the instructive part: blocking a specific exfiltration path, plus requiring explicit user confirmation before the assistant can invoke any MCP tool at all — moving the trust decision back to a human, rather than assuming anything that reaches the gateway already deserved to be there. It's a concrete illustration of why --log-calls and --verify-signatures above aren't optional hardening for a "someday" threat model; the gap they close is one that was actually exploited.

      the same architectural need, one layer up
      
Every AI-to-action path needs a policy enforcement point

      
The gateway's real job, underneath the discovery and routing conveniences, is being the one place a policy decision gets made before an agent's intent becomes an actual side effect. That's not a pattern specific to MCP — it's the same shape we build into AI-driven infrastructure changes at StackGen: the AI can propose a change, but something structurally separate from the AI's own reasoning has to evaluate that proposal against policy before it's allowed to execute against real infrastructure.

      
The Ask Gordon incident is a clean illustration of what goes wrong when that enforcement point is missing or too trusting: the assistant's reasoning and the system's authorization collapsed into the same step. Wherever an AI's output can trigger a real action — a tool call, an infrastructure change, a production deploy — that has to stay two separate steps, evaluated by two different pieces of logic.
