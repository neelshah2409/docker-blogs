Building Your First Agentic Stack with Docker Compose

Models, tools, and agent code together, defined once, launched with one command. No SDK-hopping, no hand-written glue between three different services that were never designed to talk to each other.

Estimated time 14 min Difficulty intro–intermediate Requires Docker Compose
the problem

Agent stacks usually start as a patchwork

A working agent needs at least three things: a model to reason with, a set of tools it can actually call, and application code that ties the two together with your business logic. In practice, those three pieces tend to come from three different places — a hosted model API with its own SDK, a hand-rolled integration for each tool you want the agent to use, and a bespoke script wiring credentials and endpoints between them. None of it was built to be composed; it just eventually is, through trial and error.

Docker Compose already solves this class of problem for ordinary multi-service apps — a database, an API, a frontend, one file, one command. The same shape works for agent stacks once you treat the model and the tool layer as services too.

Model Runner

Runs an open-weight model locally and exposes it through an OpenAI-compatible endpoint — no separate model server to stand up by hand.

MCP Gateway

A single service that hosts one or more Model Context Protocol tool servers and exposes them to your agent over one endpoint, instead of one integration per tool.

compose.yaml

The one file where the model, the gateway, and your agent's code are all declared together — and the only thing you hand anyone else who needs to run the stack.

prerequisites

What you need before you start

A recent Docker Desktop with Compose v2 and Model Runner support, and enough local RAM to run a small open-weight model comfortably — a 4B-parameter model at 4-bit quantization is a reasonable default for following along on a laptop.

Verify your setup
# Confirm Compose is available and check the version
docker compose version

Launch the whole stack

      
With the file saved, one command builds the agent image, pulls the model and gateway images, and starts all three services wired together:

      

        

        
# First run pulls the model — this can take a few minutes
docker compose up

# Rebuild the agent image after code changes, then relaunch
docker compose up --build

      framework integration
      
Wiring it into LangGraph

      
The agent service itself can run any framework that speaks to an OpenAI-compatible endpoint and an MCP-compatible tool server — Compose doesn't care which one. Here's the LangGraph side of the same wiring, using the environment variables the compose file above defined:

      
agent/app.py

      

        

        
import os
from langchain_openai import ChatOpenAI
from langchain_mcp_adapters.client import MultiServerMCPClient

# Model endpoint comes straight from the compose environment
llm = ChatOpenAI(
    base_url=os.environ["MODEL_RUNNER_URL"],
    model=os.environ["MODEL_RUNNER_MODEL"],
    api_key="not-needed-for-local-model",
)

# Tools come from the MCP Gateway, over the network Compose created
mcp_client = MultiServerMCPClient({
    "gateway": {"url": os.environ["MCPGATEWAY_ENDPOINT"], "transport": "sse"}
})

      

      
Swap this file for a CrewAI agent definition and nothing about the compose file changes — both frameworks just need a model URL and a tool endpoint, and Compose already handed them both.


      

        Common misconception
        
"I need a different SDK and a custom auth flow for every tool my agent uses."

        
What's actually true

        
That's true if each tool is its own bespoke integration. It stops being true once every tool sits behind one MCP Gateway speaking one protocol — the agent framework only ever needs to know about the gateway, never about the individual tools behind it.

      

    


    
    

      the same idea, one layer up
      
One file, one command, declared intent

      
What actually made this tutorial short is that compose.yaml describes intent — "this model, these tools, this code, wired together" — and Compose is the layer that turns that declaration into a running system, in the right order, without you scripting the startup sequence by hand.

      
That's the same philosophy behind StackGen's Intent-to-Infrastructure approach: describe what you want running, and let the platform generate and wire up the actual infrastructure to match, rather than hand-assembling it service by service. A three-service agent stack and a full cloud environment are different sizes of the same problem — declare the intent once, get a running system back.
