Docker Sandboxes vs Docker AI Governance: What Each One Actually Does

These two names get used almost interchangeably, but they answer different questions. Sandboxes asks "how does one agent run safely?" Governance asks "how do we guarantee that answer holds across every developer's machine?" Here's where the line actually sits.

Estimated time 9 min Format comparison Covers 2 products
scope

Two products, two different layers

Docker Sandboxes is per-agent isolation: each coding agent session runs inside its own dedicated microVM, with its own private Docker daemon and a credential proxy that keeps API keys out of the sandbox filesystem. It's something an individual developer installs and configures on their own machine.

Docker AI Governance is an org-wide policy layer on top of that: network access rules, filesystem access rules, and MCP access rules, defined once by an admin and enforced identically across every sandbox in the organization — no individual developer can loosen them.

Docker Sandboxes

The isolation boundary itself. Per-machine, per-developer, configured with the sbx CLI and local sbx policy rules.

Docker AI Governance

The policy layer on top. Org-wide, admin-configured, enforced through the Docker Admin Console or Governance API.

Kit

A YAML package of tools, credentials, and network rules a sandbox can load at runtime — the repeatable, shareable configuration layer for both.

when you need which

Sandboxes alone, or Sandboxes plus Governance?

Sandboxes by itself already gets you a real hard boundary — a microVM, a disposable daemon, credentials that never enter the guest. For a solo developer or a small team comfortable setting local policy per machine, that's a complete answer.

Governance earns its keep the moment "per machine" stops being good enough — multiple teams, an admin who needs to guarantee no one's local settings quietly drift, or an audit trail that has to hold up independent of what any one developer configured.

common misconception
What people assume

"We don't have real security until we buy Governance."

What's actually true

The hard isolation boundary — the microVM, the private daemon, the credential proxy — is Sandboxes, and it's active the moment a sandbox runs, with no Governance subscription required. Governance doesn't add security to an individual sandbox; it adds the guarantee that the same rules apply uniformly across every sandbox in the org, and that no single developer's machine is the exception.

the kit format

Kits: the repeatable config layer, still finding its shape

Before kits, customizing what tools a sandbox had meant installing them by hand each time, or maintaining a custom Dockerfile-based image. A kit packages that setup once — a spec.yaml declaring what to install, which credentials to inject, which domains the sandbox may reach, and which files to drop in — and it's distributed as a local folder, a ZIP, an OCI artifact, or a Git URL. A kind: mixin kit extends an existing agent; a kind: sandbox kit defines a whole agent from scratch.

      honest gaps
      
What doesn't work yet

      
Worth saying plainly, since it changes how you should evaluate this today: the isolation and credential model work now. The customization and distribution layer is still catching up.

      

        
⚠️
No automatic port publishing yet
A kit-exposed port gets an ephemeral host port unless you pin one yourself with sbx ports --publish — there's no automatic, stable mapping today.

        
⚠️
Kit parameters aren't user-configurable yet
You can't currently pass runtime arguments into a kit — that's on the roadmap, not shipped.

        
⚠️
The kit spec may still change
Kits are explicitly labeled experimental, and fields have already been renamed or replaced between releases — treat kits you write today as likely to need updates.

      

    


    
    

      why this pattern looks familiar
      
Define once, enforce everywhere isn't a new idea

      
The precedence rule underneath Governance — organization policy overrides local configuration, deny always wins, no individual can loosen what's centrally set — is the same governance shape we rely on at StackGen for infrastructure automation generally. Whether the thing being generated is an agent's sandbox policy or a Terraform plan, the pattern that scales is identical: policy defined once as a shared artifact, evaluated the same way regardless of who — or what — triggered the change, with local convenience never allowed to override the org's baseline.

      
That's the real argument for treating Governance as separate from Sandboxes rather than a checkbox inside it: centralized policy enforcement is a distinct capability with its own lifecycle, and it's worth designing that way from the start rather than bolting it on once per-machine drift becomes a problem you can already see.
