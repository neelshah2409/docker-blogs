Beyond AI Agents: Other Uses for Docker Sandboxes

Docker Sandboxes were built to solve one problem — autonomous coding agents needing real permissions without real risk. But a disposable microVM with a hard isolation boundary doesn't actually know or care what's running inside it. That's worth taking advantage of.

Estimated time 11 min Format applied use cases Builds on Sandboxing series
recap

The capability, stripped of its original use case

Underneath the "AI agent" framing, a Docker Sandbox is a fairly general primitive: a microVM with its own kernel, a private disposable Docker daemon, a scoped workspace mount, and a network policy that determines what it can reach. None of that is specific to agents — it's specific to running something you don't fully trust, and needing it to boot fast enough that the isolation doesn't get in the way of getting work done.

Widen the definition of "something you don't fully trust" past "an LLM's shell commands," and three more use cases show up almost immediately.

microVM boundary

A real second kernel, not shared namespaces — the part of the design that doesn't change no matter what workload runs inside it.

Private daemon

A disposable Docker daemon scoped to the sandbox, so whatever runs inside can build and run its own containers without touching the host's.

Network policy

The configurable part that should change per use case — what a sandbox is allowed to reach says more about the workload than the isolation itself does.

Where the same primitive applies directly

common misconception
What people assume

"For malware analysis, always cut the network entirely — that's the safest option, full stop."

What's actually true

Fully offline is safest for containment, but it can also blind you: a lot of malware's interesting behavior — command-and-control callbacks, payload staging, exfiltration attempts — only shows up once it tries to talk to the network. Analysts often deliberately allow a policy-restricted, monitored egress path (pointed at decoy infrastructure, not the real internet) so that behavior is observable instead of silently suppressed. "Locked Down" isn't automatically the right answer even when the workload is the most hostile one on this list — it depends on whether you're containing the sample or studying it.

throughput

Why the boot time number matters more here than it did for agents

For a single coding agent session, the gap between a 30-second VM boot and a 125-millisecond microVM boot is a nice-to-have. For malware analysis and CI, where the point is running the same kind of workload over and over across many samples or many commits, that gap compounds directly into throughput.

Full VM — fresh launches per minute~1–2
microVM sandbox — fresh launches per minute~450+
Derived from published ~30–60s full-VM boot times versus ~125ms microVM boot times — a rough ceiling based on boot time alone, ignoring other bottlenecks like disk I/O or analysis duration itself. Real-world throughput will be lower once the workload inside is actually doing something.

In practice, that ceiling means a malware analysis pipeline can push a sample through many different tool configurations in the time a single full-VM run would have taken, and a CI system can give every commit — not just every merge to main — its own completely fresh, disposable environment without the boot cost becoming the bottleneck.

practical guidance

Choosing a network policy per use case

Use caseTypical policyWhy
Malware analysis (containment)Locked DownNo path out at all — the safest default when the goal is preventing spread, not observing behavior
Malware analysis (behavioral study)Balanced, pointed at decoy infrastructureLets C2 and exfiltration attempts happen somewhere observable instead of being silently blocked
Untrusted third-party / user-submitted codeBalanced or Locked DownMost platforms only need package registries, if that — default to the narrowest policy the workload actually requires
Ephemeral CI / build pipelinesBalancedNeeds package registries and possibly artifact storage, but no reason to reach arbitrary hosts

the broader pattern

Ephemeral and policy-governed is becoming the default shape

What ties these three use cases together isn't agents, or security research, or CI specifically — it's a shape: an environment that's cheap enough to throw away that you stop trying to keep it clean, paired with a policy that's explicit enough that "throwaway" doesn't mean "unrestricted." That combination is showing up everywhere platform teams provision environments on someone else's behalf, not just where AI agents are involved.

That's the same shape we design for at StackGen when generating infrastructure: environments that are disposable by default and governed by an explicit, centrally defined policy rather than by whoever happened to configure that particular instance. Sandboxes, preview environments, CI runners, and agent workspaces are different names for the same underlying pattern — and the platforms that treat it as one problem, not four, are the ones that scale it without re-solving it each time.
