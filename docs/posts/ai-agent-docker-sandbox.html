How to Run Your First AI Coding Agent in a Docker Sandbox

Coding agents like Claude Code and Cursor are most useful with full shell and filesystem access — which is exactly what makes one wrong command dangerous. Here's how to give an agent a real machine to work in without giving it yours.

Estimated time 15 min Difficulty intro–intermediate Requires Docker Desktop 4.58+
the problem

Agent autonomy and blast radius are the same feature

An AI coding agent is genuinely useful the moment you give it a real shell: it can install packages, run your test suite, edit files across the repo, and fix what it breaks. That's also the entire risk surface. A hallucinated rm -rf, a malicious transitive dependency, or a prompt-injected instruction hidden in a scraped web page all execute with exactly the same permissions as your own terminal — because right now, they usually run in it.

None of this requires the agent to be malicious. It just needs to be wrong once, with the same access you have.

Full shell access

The agent can run any command your user account can — install, delete, curl, push to git — with no distinction between "reading a file" and "wiping a drive."

Blast radius

Everything a single mistaken or malicious action can reach. On your host machine, that's your whole filesystem, SSH keys, and network. In a sandbox, it's one disposable folder.

Prompt injection

Instructions hidden in content the agent reads — a README, a webpage, a GitHub issue — that get executed as if you'd typed them yourself.

Analogy

Giving an agent your real machine's shell is like handing a new contractor the master key to the entire building because they only need to fix one office. A sandbox is giving them a key to that one office instead.

prerequisites

What you need before you start

Two things: Docker Desktop 4.58 or later (it added the microVM runtime this sandbox relies on) and the sbx CLI, which wraps Docker with sandbox-specific defaults so you're not hand-rolling isolation flags every time.

Install and verify
# Install the sbx CLI
curl -fsSL https://get.sbx.dev | sh

# Confirm both are ready
docker --version   # Docker Desktop 4.58.0 or later
sbx --version
step-by-step

Set up and launch your first sandboxed agent

1. Run the one-time setup

sbx setup provisions the microVM runtime and pulls the private Docker daemon image the sandbox uses internally. You only run this once per machine.

# Provisions the microVM + private daemon, one time only
sbx setup

2. Choose a network policy

This is the single most important decision in the whole setup. It controls what the agent can reach outside its own sandbox.

3. Launch the agent from your project directory

From inside the project you want the agent to work on, point sbx run at your config and go:

# Scoped to this directory, using sbx.yaml below
sbx run claude-code --project . --config sbx.yaml

That config file is where the isolation actually gets defined — click through it below.

      shared context
      
Give the agent vetted skills, not a blank slate

      
A sandboxed agent that starts from scratch every session tends to reinvent its own approach to your team's conventions — Terraform review checklists, migration playbooks, code style rules. sbx skills import pulls a pre-approved skill bundle from your team's shared skills store instead, so every sandbox run starts from the same reviewed instructions rather than whatever the agent improvises.

      
Import and list available skills

      

        

        
# Pull a vetted skill bundle into the sandbox
sbx skills import terraform-review

# See everything your team has published
sbx skills list --store shared

      

      
Because the store is shared, a skill one engineer wrote and reviewed once — say, "how we review Terraform diffs" — is available to every sandboxed agent run on the team from that point on, without anyone re-explaining it in a prompt.

    


    
    

      common misconception
      

        What people assume
        
"It's running in a container, so I can mount my whole home directory and skip the network policy — nothing bad can actually happen."

        
What's actually true

        
Isolation is only as strong as the scope you give it. Mounting more than the project directory hands the agent write access to files that have nothing to do with the task. Skipping the network policy (defaulting to Open) means a prompt-injected instruction can still exfiltrate data or pull down something you didn't ask for. workspace.readonly_root and a deliberately chosen network policy aren't optional extras — they're the two settings doing most of the actual protecting.

The result: the agent gets a fully functional Linux environment with its own kernel boundary (not just container namespaces), its own throwaway Docker daemon for anything it builds or runs, and — depending on the policy you picked — no path back to your host filesystem or network at all.

    


    
    

      why this matters beyond one agent session
      
Sandboxing is the floor, not the ceiling

      
Running one agent safely in a terminal is a good habit. But the same problem shows up at a larger scale the moment you let AI propose or apply changes to actual infrastructure — a Terraform plan, a Kubernetes manifest, a production config. The same principle this tutorial just walked through still applies: an agent should never get more filesystem, network, or execution access than the specific task requires, whether that task is refactoring a function or provisioning a VPC.

      
Sandboxed execution isn't a nice-to-have bolted on afterward — it's the prerequisite everything else in AI-driven infrastructure automation sits on top of.


      
        
Beyond this tutorial

        
Apply the same sandboxing model to infrastructure changes

        
The same isolate-first discipline — scoped filesystem access, an explicit network policy, disposable execution — holds up just as well when an agent is proposing changes to real infrastructure, not only editing code.
